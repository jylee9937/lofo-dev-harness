# lofo-dev-harness 설계 (초안)

> 상태: 설계 단계 (2026-11-23). 아직 설치할 수 있는 코드는 없습니다.

## 1. 목적

Claude Code를 오케스트레이터로, Codex를 구현·리뷰 워커로 두고 프로젝트를 만들 때 쓰는 **공용 하네스**입니다.
실제로 운영한 사이드 프로젝트 세 개의 하네스를 하나로 합칩니다.

가장 큰 목표는 **복사본이 갈라지는 문제를 없애는 것**입니다. 지금까지는 같은 규칙·훅·스킬·스크립트를 프로젝트마다 복사해 썼고, 시간이 지나며 모델명·검사 스크립트·문서 형식이 서로 달라졌습니다.

## 2. 출발점: 세 프로젝트의 하네스

```
전역 스킬 start-coding (브랜치 만들고 하네스 불러오기)
        │ 복사
        ▼
A. 강의 플랫폼       (원조 "개발 하네스")
        │ 이식 (일부 연동을 빼고 맥락 관리를 노트 앱으로 옮김)
        ▼
B. 웹사이트

C. 웹사이트          (따로 발전한 자율 운영형: "AI가 만들고 오너는 결정만")
```

세 프로젝트 모두 Next.js + Supabase + Vercel + pnpm, FSD 구조입니다.

| | A. 강의 플랫폼 | B. 웹사이트 | C. 웹사이트 |
|---|---|---|---|
| 진입점 | `CLAUDE.md → @AGENTS.md` | 같음 | 같음 + 별도 하네스 문서 |
| 운영 방식 | 사용자와 함께. 커밋·PR은 요청할 때만 | 같음 | 00~08시 자율 작업, 09시에 결정 질문, `main` 병합도 AI가 |
| 작업 단위 | 기능 하나 = 브랜치 하나 = PR 하나 | 같음 | 작업 묶음마다 worktree·포트·로컬 DB 하나씩 |
| Codex 역할 | 구현·리뷰·진단을 먼저 맡음 | 같음 | 보안 검토(필수) + 구현 |
| 강제 장치 | 소스 수정 시 "Codex 먼저" 알림 훅 (막지는 않음) | 같은 훅의 다른 버전 | CI 9개 job + 오프라인 검사 11종 |
| QA | QA 하네스, 다중 에이전트 QA 설계, 매트릭스, 루브릭 | QA 하네스 (줄인 판) | Playwright 전체 경로 + axe |
| 작업 기록 | 로컬 칸반 + 핸드오프 파일 | 핸드오프 파일 여러 개 | git 안의 핸드오프 문서 |

## 3. 세 곳에 공통인 것 (core 후보)

1. **진입점**: `CLAUDE.md`에는 `@AGENTS.md` 한 줄만 둡니다. Claude와 Codex가 같은 규칙을 읽고, 요약은 `AGENTS.md`, 상세는 `docs/`에 둡니다.
2. **역할 분담**: Claude는 나누고·판단하고·합치고·기록합니다. Codex는 높은 effort로 구현·리뷰·진단을 맡습니다. 한도가 차면 Claude 상위 모델 → 중간 → 하위 순으로 내려갑니다.
3. **안전 규칙**:
   - `main`에 바로 커밋하지 않습니다.
   - 외부 쓰기, 배포, 호스팅 DB 변경은 확인을 받은 뒤 합니다.
   - 비밀값은 출력하지도 저장하지도 않습니다.
4. **백엔드는 설명하면서 함께 결정**: 권한(RLS), 마이그레이션, 서버 키 같은 부분은 개념과 장단점을 설명하고 기술설계 문서로 남깁니다.
5. **완료 기준 = 검사 통과 + e2e**: 손으로 하는 스모크 확인으로 끝내지 않습니다. 검증하지 못하면 이유와 다음에 돌릴 명령을 남깁니다.
6. **QA 전용 포트**: 다른 worktree의 개발 서버를 잘못 테스트하지 않도록 QA는 별도 포트를 씁니다.
7. **문서 3단계**: 작업 과정(로컬 메모·핸드오프) → 확정 스펙(`docs/`, git) → 맥락과 판단(노트 앱 등 외부 기록).
8. **Codex 운용 요령**:
   - 위임은 기본이 쓰기 모드입니다. 진단만 시킬 때는 read-only라고 적고, 끝나면 `git status`를 확인합니다.
   - 모델을 적지 않으면 전역 기본값으로 돌아가므로 매번 명시합니다.
   - 마지막 답이 빈 보고일 때는 transcript에서 실제 결과를 꺼냅니다.
9. **디자인 규칙**: 색은 토큰만, 외부 이미지 금지(검사 스크립트로 강제), 디자인 기준은 Figma.
10. **구조**: FSD 아키텍처.

## 4. 한 곳에만 있지만 가져올 것

**C (가장 많이 다듬어짐)**
- Codex 실행 스크립트 세 개:
  - 백그라운드 실행 후 완료 파일로 결과를 받는 러너
  - 한도에 걸리면 초기화 시각까지 기다렸다 다시 돌리는 재시도기
  - 구현 → 커밋 → CI → 검토(최대 3회) → 수정을 반복하고 `GO/NO-GO`로 끝내는 연쇄 실행기
- ★ 보안 관문: 인증·돈·비밀값·권한은 Codex 검토 필수. Claude 대체 검토가 GO라고 했는데 Codex가 막아야 할 문제를 찾은 사례가 근거로 남아 있음.
- 에이전트 지시문 공통 끝부분, 검토 지시문 head/tail 템플릿.
- 자율 야간 운영: 한도 읽기, 정해진 시각의 예약 작업, 아침 정리 절차, 오너 질문 목록, 밤 계획.
- worktree 슬롯·포트 규칙, 로컬 DB 잠금, 마이그레이션 번호 미리 나눠 주기.
- 네트워크 없이 돌아가는 병렬 검사(샌드박스 안에서도 실행 가능).
- 만료일이 있는 검사 예외 목록.
- 호스팅 DB 반영 절차: 백업 → dry-run → 사전 확인 SQL의 GO 조건 → push → 결과 확인.
- "알려진 함정" 표와 "바뀐 규칙" 날짜 기록.

**A**
- QA 4단계: 스크립트 검사 → 판단 에이전트 여러 개 → 반박 검증 → Codex 수정.
- 공용 findings JSON 형식, 심각도 S1~S4, 시각 리뷰 루브릭.
- 파일 칸반(`todo → in-progress → done`)과 확정된 것만 `docs/`로 올리는 승격 규칙.
- 8단계 프로세스: 개발 전 문서 3종(요구, 화면, 기술설계)마다 검토 단계, 기술설계 문서 필수 6개 섹션.
- 브라우저 테스트 안전 규칙: 역할별 쿠키 분리, 운영 사이트에서는 쓰기 동작 금지.

**B**
- Tailwind v4가 utilities를 비운 채 빌드만 통과하는 사고를 잡는 검사.
- 위젯과 데이터 사이 약속을 적은 `CONTRACT.md` (data-provider 패턴).
- 저장소 간 요청서(`REQUEST-*.md` / `REPLY-*.md`): DB를 가진 저장소에 스키마·권한 변경을 부탁하는 형식.

## 5. 서로 어긋난 곳 (공용 하네스가 풀어야 할 문제)

| 문제 | 상태 |
|---|---|
| 모델명이 여러 군데 박혀 있고 서로 다름 | 문서마다 Claude·Codex 모델명이 다르고, 실제 쓰는 모델과도 다름 |
| Codex 호출 방식 | `-c model=…`, `-m …`, 러너 스크립트 세 가지가 섞임 |
| 복사본이 갈라짐 | 라우팅 훅 2벌, 시작 스킬 3벌, QA 스크립트 2벌, 외부 이미지 검사 3벌 |
| 예전 예시가 남음 | 시작 스킬 예시에 다른 프로젝트 예시가 그대로 |
| 핸드오프 파일 비대 | 수백 KB까지 커져 새 세션이 다 읽을 수 없음 |
| 권한 방식 차이 | 협업형(요청할 때만 커밋) vs 자율형(AI가 병합) |
| 개인 경로가 코드에 박힘 | 홈 디렉터리 절대 경로, 실행 파일 경로, 클라우드 프로젝트 ID |

## 6. 결정 사항 (2026-11-23)

1. **운영 방식**: 공통 core 위에 **협업 모드**와 **자율 모드**를 따로 켜는 모듈로 얹습니다. 협업으로 시작해 익숙해지면 자율로 넘어가는 흐름을 그대로 따릅니다.
2. **스택 범위**: 스택에 묶이지 않는 core + 프리셋. init에서 **DB, 서버·배포 방식을 질문해서 결정**합니다 (예: Supabase / Firebase, Vercel / GCP / AWS 직접 서빙). 첫 프리셋은 Next.js + Supabase + Vercel.
3. **배포 형태**: Claude Code **플러그인 마켓플레이스** + 프로젝트 파일을 질문하며 만드는 **init 스킬**. 스킬·훅·에이전트는 플러그인 한 곳에서 관리해 업데이트가 모든 프로젝트에 반영됩니다.
4. **언어**: README·스킬 본문은 영어, `README.ko.md`는 별도. init에서 프로젝트 문서 언어(ko/en)를 고르면 그 언어로 템플릿을 만듭니다.
5. **플러그인 이름**: 저장소·마켓플레이스·플러그인 모두 `lofo-dev-harness`. 스킬은 `/lofo-dev-harness:init`처럼 부릅니다.
6. **라이선스**: MIT.
7. **화면 설계·UX 검토** (2026-11-24): 디자인 도구(Pencil, Figma, 기타)로 시안을 그리는 것과 함께, 와이어프레임 위에 UX 검토 표시를 보여 주는 기능을 하네스에 넣는다.
   - 참고한 wireflow-review는 라이선스가 없어서 코드는 쓰지 않는다. 도구와 무관한 **자체 흐름 모델**(`design/flows/<id>.flow.json`)을 정본으로 두고, 검사 스크립트, HTML 보드, 디자인 도구 표시 규칙을 직접 만든다.
8. **보드 수준**: 첫 버전은 **검토 보드**다.
   - 단계별 화면, 번호 붙은 경로 강조, 화면별 검토 표시, 수정 요청 복사가 들어간다.
   - 버튼을 눌러 걸어 보는 클릭 프로토타입(입력값 유지, 실패 후 재시도 재현)은 다음 버전으로 미룬다.

## 7. 저장소 구조안

✅ = v0.2에 있음, 나머지는 예정.

```
lofo-dev-harness/
├─ .claude-plugin/
│  ├─ plugin.json              ✅ 플러그인 정보
│  └─ marketplace.json         ✅ 이 저장소를 바로 마켓플레이스로 등록
├─ skills/
│  ├─ init/                    ✅ 질문을 하나씩 받아 설정을 쓰고 프로젝트 파일 생성
│  ├─ start-task/              ✅ 기본 브랜치 최신화 → 브랜치 생성 → 하네스 로드
│  ├─ codex-delegate/          ✅ Codex 위임 규칙, 지시문 틀, 결과 회수 요령
│  ├─ wireflow/                ✅ 흐름 작성 → 검사 → UX 검토 → 보드 → 디자인 도구 표시 → 수정 요청 반영
│  │  └─ references/           ✅ UX 체크리스트, 디자인 도구별(Figma, Pencil, 기타) 표시 규칙
│  ├─ security-gate/           # ★ 관문: 인증·돈·비밀값·권한은 Codex 검토, GO/NO-GO
│  ├─ tech-design/             # 기술설계 문서 6개 섹션, 백엔드 설명 규칙
│  ├─ qa/                      # L0~L3 QA 단계, findings 형식, 시각 리뷰 루브릭
│  ├─ handoff/                 # 핸드오프 작성·정리 (크기 상한)
│  └─ night-shift/             # 자율 모드 전용: 밤 계획, 아침 정리, 오너 질문 목록
├─ hooks/
│  ├─ hooks.json               ✅
│  └─ codex-routing-reminder.py ✅ 감시할 경로 패턴을 프로젝트 설정에서 읽음
├─ agents/                     # QA 판단 에이전트 (시각, 흐름, 반박 검증)
├─ scripts/
│  ├─ render.py                ✅ 설정 → AGENTS.md 블록, CLAUDE.md, 하네스 문서, .gitignore
│  ├─ flow.py                  ✅ 흐름 검증·구조 검사(check) → HTML 검토 보드(build)
│  └─ …                        # Codex 러너·재시도·연쇄 실행, DB 잠금, worktree 생성
├─ templates/{ko,en}/          ✅ 두 언어가 같은 파일 구성
│  ├─ AGENTS.block.md, dev-harness.md
│  ├─ modes/{collab,autonomous}.md
│  ├─ framework/{nextjs,_generic}.md
│  ├─ db/{supabase,none,_generic}.md
│  └─ hosting/{vercel,_generic}.md
├─ templates/wireflow/board.html ✅ 검토 보드 템플릿 (외부 의존성 없음, 라이트·다크, 휴대폰 폭)
├─ schemas/                    ✅ .harness/config.json 스키마, 흐름(flow.schema.json) 스키마
├─ examples/                   ✅ 설정 예시, 예시 흐름(flows/study-group.flow.json)
├─ tests/                      ✅ 렌더러·훅·흐름 테스트 (unittest)
├─ docs/                       # 하네스 자체 설명 (개념, 모드, 프리셋 만드는 법)
├─ README.md / README.ko.md    ✅
└─ LICENSE                     ✅
```

프리셋이 없는 값(Firebase, PostgreSQL, GCP, AWS, 기타 프레임워크)은 `_generic.md`가 쓰입니다. 일반 원칙만 들어가고, 구체 규칙은 프로젝트가 직접 채웁니다.

## 8. 설정은 한 곳에: `.harness/config.json`

init이 프로젝트에 설정 파일 하나를 만들고, 훅·스크립트·스킬은 모두 이 파일을 읽습니다.
모델이 바뀌면 이 파일 한 곳만 고칩니다.

- 형식: [`schemas/harness-config.schema.json`](../schemas/harness-config.schema.json) (JSON Schema 2020-12)
- 예시: [`examples/nextjs-supabase-vercel.config.json`](../examples/nextjs-supabase-vercel.config.json), [`examples/autonomous.config.json`](../examples/autonomous.config.json)

| 항목 | 내용 |
|---|---|
| `version`, `language`, `mode` | 설정 형식 버전, 문서 언어(ko/en), 운영 모드(collab/autonomous) |
| `stack` | 프레임워크, DB(supabase/firebase/postgres/none/other), 배포(vercel/gcp/aws/other), 패키지 매니저 |
| `models` | Codex 사용 여부·모델·effort (사용하면 모델 필수), Claude fallback 순서 (opus 같은 별칭 사용) |
| `gates`, `e2e` | 완료 전에 모두 통과해야 하는 명령. 오프라인 실행 가능 여부 표시 |
| `qa` | QA 전용 포트, 시각 리뷰 뷰포트 |
| `codexRouting` | 라우팅 훅이 쓰는 경로 정규식 (소스 코드, 제외, 백엔드 민감 경로) |
| `docs` | 하네스 문서·핸드오프 위치, 핸드오프 크기 상한 |
| `integrations` | 노트 앱, 디자인 도구, gstack, 할 일 앱 |
| `autonomous` | 자율 모드일 때 필수: 시간대, 작업 시간, 정리 시각, 결정 질문 시각, 주간 사용량 상한 |

로컬 경로처럼 내 컴퓨터에만 해당하는 값은 이 파일에 넣지 않고, git에서 제외되는 `.harness/config.local.json`에 둡니다.

## 9. init이 묻는 것 (하나씩)

1. 프로젝트 문서 언어 (ko / en)
2. 운영 모드 (협업 / 자율)
3. 프레임워크: 자동 감지 후 확인
