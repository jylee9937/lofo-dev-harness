### Codex에 맡기는 방법

- `/lofo-dev-harness:codex-delegate` 스킬을 따른다.
- 모델과 effort는 `.harness/config.json`의 `models.codex`에서 읽어 **매번 명시**한다. 빼면 Codex 전역 기본 모델로 조용히 바뀐다.
- 전역 Codex 설정(`~/.codex/config.toml`)은 바꾸지 않는다. 다른 프로젝트와 같이 쓰는 파일이다.
- 진단·리뷰만 시킬 때는 read-only로 맡긴다. 쓰기 모드로 맡겼다면 끝난 뒤 `git status`와 `git log main..HEAD`로 무엇이 바뀌었는지 확인한다.
- Codex의 마지막 답이 "완료했습니다" 같은 빈 보고면 실행 로그에서 실제 결과를 찾는다.

## 2. 프로세스

개발 전 산출물은 **작성 → 검토 → 확정**을 거쳐야 다음 단계로 넘어간다. 작은 버그 수정과 변경은 5~7단계만 거친다.

| # | 단계 | 산출물 | 검토 |
|---|---|---|---|
| 1 | 기획·요구 | 요구사항과 수용 조건 | 제품·범위 검토 |
| 2 | 화면 설계 | {{design_source}} | 화면 검토 |
| 3 | 기술 설계 (필요할 때) | `docs/<기능>-tech-design.md` | 아키텍처 검토 |
| 4 | 데이터 정합 점검 | 스키마·권한 규칙을 실제 DB 기준으로 확인 | 마이그레이션 diff, 권한 실검증 |
| 5 | 개발 | 코드와 작업 브랜치 | — |
| 6 | QA | 검사·e2e 통과 기록, 코드 리뷰 | §7 |
| 7 | 배포 | PR 병합과 배포 | §3, §5 |

검토 방법: {{#gstack}}gstack 스킬 (기획 `/plan-ceo-review`, 화면 `/plan-design-review`, 기술 `/plan-eng-review`).{{/gstack}}{{^gstack}}Claude 서브에이전트에게 분석·아키텍처·비평 역할을 맡긴다{{#codex}}. Codex에게 2차 의견을 받는다{{/codex}}.{{/gstack}}

### 기술 설계 문서 필수 섹션

1. **데이터 모델**: 테이블·컬럼·인덱스·제약, 권한 규칙(공개 읽기 / 본인만 / 운영자), 공개 범위, 마이그레이션 계획
2. **서버 경계·인가**: 관리자 키를 쓰는 곳, 서버 액션과 라우트 핸들러 중 무엇을 쓰는지와 가드가 덮는 범위
3. **API·쿼리**: 공개·관리 쿼리, 페이지네이션, 캐싱
4. **코드 배치**: 새로 생기는 모듈과 라우트
5. **외부 연동·규정**: 결제, 개인정보, 수신 동의
6. **리스크·대안**: 트레이드오프, MVP 범위

## 6. 백엔드 협업 규칙

백엔드를 건드릴 때 Claude는 **먼저 개념·선택지·트레이드오프를 설명하고 사용자와 함께 정한 뒤** 구현한다. Codex가 코드를 써도 설명은 Claude가 한다.

대상:
- 권한 규칙 (RLS, 보안 규칙): 공개 읽기 / 본인만 / 운영자 역할
- 마이그레이션: 컬럼, 인덱스, 권한, 공개 범위
- 관리자 키처럼 권한 규칙을 우회하는 자격 증명을 쓰는 곳
- 서버 경계: 서버 액션과 라우트 핸들러, 가드가 덮는 범위
- 결제, webhook 같은 외부 연동

설명에는 개념, 왜 그 선택인지, 대안이 들어가야 한다. 결정과 트레이드오프는 기술 설계 문서(§2)에 남긴다.
